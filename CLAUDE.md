# CLAUDE.md

`session` is one bash CLI (`session`), its status line (`statusline.sh`), an installer (`install.sh`, `uninstall.sh`), and a plugin carrying a skill (`skills/session/SKILL.md`) and a hooks module (`hooks/register.ts`, which registers `hooks/reload-on-switch.ts`, `hooks/rate-limit-menu.ts` and `hooks/compact-before-switch.ts`, all reading the main loop's turns through `hooks/main-loop.ts`: one plugin may hook an event only once without a matcher, which is why the last takes `session.start` with `{ isInteractive: true }`). README.md is the contract for users and anything that reads the CLI's output; this file is for changing the code.

## Commands

```
bash tests/run.sh                  # every suite
bash tests/session.test.sh         # one suite
claude plugin test .               # the hooks module's tests alone (hooks/*.test.ts)
```

## Tests

- **Branches that have never run:** `proc_env`'s `ps -Eww` fallback (Darwin-only; its case always skips), `mtime_of`'s BSD `stat -f %m`, and the macOS Keychain shape of `session account`, which the suite simulates by removing `.credentials.json` rather than testing it.
- **The hooks module's tests run on Claude Code's engine**, not in bash: `tests/plugin.test.sh` wraps `claude plugin validate` and `claude plugin test` and skips without `claude` on `PATH`. Types are not in the repo: Claude Code lays them in `.claude-plugin/types/` when it loads the clone with `--plugin-dir`, and its plugin-authoring skill's `types/claude-code.d.ts` carries the `tsconfig.json` to check against.
- **The compaction hold's assumptions about Claude Code and tmux were observed by hand on 2.1.301** and are listed in the comments above `--post-tool-batch` and `--compact-gate` in `session`; the suite covers the decisions against stubs only (its stdin is a pipe, Claude Code's a socket, which case 28 reproduces). Re-check them after a Claude Code update that touches compaction or hooks; the end-to-end run needs a tmux client attached under a pty that types.
- **Never touch the real `<config dir>/.session-login-switch` or `.session-switch-soon` to test the hooks module live**: every running session on the machine polls them, so a touch reloads or compacts them all. Run a throwaway `claude --plugin-dir <clone>` on its own `tmux -L <name>` server with `SESSION_LOGIN_SWITCH_MARKER` (and `SESSION_SWITCH_SOON_MARKER`, `SESSION_PRE_SWITCH_COMPACT_FLOOR` to make a small session qualify) pointing at scratch paths, write the marker there (or run `session account use` against a scratch `CLAUDE_CONFIG_DIR` and set the variable to its marker), and read the row with `tmux capture-pane -p`.
- **The mid-turn half of `hooks/compact-before-switch.ts` rests on how Claude Code 2.1.325 treats a `turn.step` hook that answers without `next`**: no request is sent, the turn ends with reason `answer` and its tool results intact, and `$.session.compact()`, with `$.prompt.submit()` called while it runs and held by the engine until it is done, carry it on (the module's comment says what was seen). Re-check it by hand after an update that touches either call.
- **The runs marker's right alignment rests on Claude Code drawing the status row in `COLUMNS - 4` cells**, measured by hand on 2.1.310: a throwaway session (as above, with `clip` stubbed on `PATH` where a Stop hook would copy to a clipboard) whose status line prints a ruler of `COLUMNS - k` cells shows it whole at k=4 and cut with `…` at k=3. Re-measure after a Claude Code update that touches the status line; the suite checks the padding arithmetic against that number only. `--safe-mode` turns the status line off, so the throwaway cannot use it.
- **The close compaction's hook handling (`lib/closecompact.sh`) rests on what Claude Code 2.1.326 was seen to do**, by hand, on throwaway sessions each on its own `tmux -L <name>` server with a project-level `.claude/settings.json` wiring probe scripts on the hook events (never a session you did not start, and not the real `settings.json`). Survival: a `SessionEnd` entry with `timeout: 2` whose probe starts five waiters, each sleeping 20 s and then writing a file, and then sleeps 6 s itself, is killed at the timeout with its process group and its descendants. The five: a subshell `( cmd & )` that stays in the hook's group; `setsid -f cmd`; perl `fork` + `POSIX::setsid` + `exec`; a subshell `( setsid cmd & )`; `nohup cmd &`. Only the three that leave the group and the hook's descendants (`setsid -f`, the perl one, the subshell `setsid`) wrote their file; the subshell in the group and `nohup` died. With a probe that returns at once all five survive a `/exit` and a `tmux kill-pane`. Environment: the hook's `CLAUDE_CODE_ENTRYPOINT` is `cli` for an interactive session and `sdk-cli` for `claude -p`, also when `claude -p` is started from inside a session's shell with `CLAUDE_CODE_ENTRYPOINT=cli` in its environment; a variable set on the `claude -p` command line reaches its hooks; the payload's `cwd` follows a `cd` the shell made while the transcript stays filed under the launch folder's name; a closed session's registry record is gone by the time its hook runs, and a headless resume registers there under its own pid with `kind: interactive`, `entrypoint: sdk-cli`; killing the run leaves no compaction row and the session resumes. The deciding test is whether a hook entry that outlives its timeout still leaves a waiter running.
- **The close compaction's cache behaviour is what makes it worth running.** Measure the run's own usage as the result's `modelUsage` less the last `cost-state` row of the transcript (the result's `total_cost_usd` is the session's whole cost, the earlier part restored from that row). Opus 5.5: a throwaway session of many requests and 468,000 tokens, closed, then compacted from its launch folder on the model of its last request, read 449,875 cache tokens, wrote 114 and cost $0.20; reopened, its first request carried 63,000. Fable 5.2: a 126,618-token session read 126,611, wrote 5 and cost $0.21 (obs capture `F-fable-compact.stdout`). Run from `/tmp`, a second compaction of that already compacted, reopened 63,000-token Opus session read 11,315 and wrote 50,396 ($0.44): the launch folder matters. A conversation of one request was not served from the cache, which is rare at the floor (only a first request of 200,000 tokens passes it); with a plain prompt instead of `/compact` an interactive session's cache is missed because the request's thinking display differs (`updates` against `omitted`). The clock rests on the transcript's `api-request` rows: each main-loop request has one (source `repl_main_thread`, or `sdk` for a headless resume) written when it is sent, 6.6 s before its answer rows for the last request of the Opus capture; a subagent's requests have rows in its own file under source `agent:<type>`; `cacheControl[].value.ttl` is `1h` with `promptCacheTtl` set to `1h` and absent with `5m`, which the code reads as the default five minutes. Re-check after an update that touches hooks, `--resume`, `/compact` in print mode or the request's shape.
- **The README cites no test cases.** To find the test behind a promise, grep the suites for the behaviour.
- **Sourcing `lib/common.sh` rebinds `SESSION_DATA`** from `SESSION_DATA_DIR`, `session.conf` and the defaults, so a scratch script that sets `SESSION_DATA` and then removes it deletes the machine's real data root. Clean up scratch by a literal path, never by that variable.

## Conventions

- **The hooks module runs in Claude Code's plugin engine**: TypeScript with no Node and no DOM, reaching files, timers and commands only through `$`. Its API is early access and moves between releases, so keep it to the few calls it makes. `tests/plugin.test.sh` catches API drift only, against a mocked engine; what the module relies on (claude.ai connectors move to the new login's ids on `/reload-plugins`) is checked by hand, by switching logins under a live session and calling a connector. The note on the reload row (`/reload-plugins login switched from A to B (reason)`) rests on `/reload-plugins` ignoring its arguments and Claude Code drawing a plugin-run command row as typed (observed on 2.1.301).
- **bash 3.2 clean, no GNU-only tool without a fallback.** macOS ships bash 3.2, BSD `date`/`stat`, no `/proc` and no `flock(1)`. Dates go through perl, `stat` through `mtime_of`, processes through `/proc` with a `ps` fallback, locks through `flock(1)` with a perl fallback; the comment at each fallback says why it is shaped the way it is. README "Platform support" states only what a user sees. Case 1 greps shipped scripts for bash 4/5 constructs that a syntax check misses.
- **Public repo.** Case 13 greps for host names and hardcoded home paths; no personal, employer or machine names anywhere in the tree or in commit messages (a pre-push hook on the clone refuses them).
- **Mechanism lives in comments at the writer.** The README states the contract (commands, config, data files, schemas, the `time --json` fields a task logger reads); why a code path is shaped the way it is goes in a comment beside it. Change the README only when the contract changes, and keep the headings other tools cite (the skill and `--help` point at "`time --json` — the contract a task logger reads").
- **Help, skill, README.** A new flag goes in `session --help` (or the verb's `-h`); the skill gets a line only if a session would otherwise use the tool wrongly.
